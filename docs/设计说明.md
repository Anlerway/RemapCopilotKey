# 设计说明

本文说明 RemapCopilotKey 的架构决策、状态机细节与取舍理由。
配置字段与命令行参数见文末附录（第 15、16 节）。

---

## 1. 问题定义

微软在 *Windows Copilot Key Guidance for Ecosystem Partners* 中规定，Copilot 键在
**固件层**就上报三个真实按键：

```
按下： make LWIN  →  make LSHIFT  →  make F23
松开： break F23  →  break LSHIFT →  break LWIN
长按： 三个键按 Win / Shift / F23 的顺序重复上报
```

并且当键盘没有多余键位时，微软**要求**用它替换掉右 Ctrl。BIOS 与 Windows 设置都没有
改回来的开关。

这产生了两个硬约束：

| # | 约束 | 后果 |
|---|---|---|
| 1 | Copilot 键是**三个真实按键**，不是"一个特殊键" | 任何**无条件替换扫描码**的方案都不成立。必须做**条件性 / 序列判定** |
| 2 | Windows 用户态输入路径有 **UIPI 隔离** + **安全桌面隔离** | 任何用户态方案都看不到送往提升窗口的输入，也永远看不到 UAC 提示与登录界面 |

本项目的全部设计都是在这两条约束下做的选择。

## 2. 总体架构

两个进程，两条通道：

```
┌───────────────────────────┐                    ┌────────────────────────────┐
│ RemapCopilotKey.exe        │                    │ RemapCopilotKeyService.exe │
│ (C# / WPF, 管理员)          │                    │ (C++ / Win32, 后台静默)     │
│                            │                    │ (C++ / Win32, 管理员)       │
│  · 写配置                  │                    │                            │
│  · 多语言界面              │   ① config.json    │  · WH_KEYBOARD_LL 钩子     │
│  · 启停服务                │ ◀───────────────── │  · 三键序列状态机          │
│  · 注册自启服务 (SCM)      │   ② 窗口消息       │  · 动作执行                │
│                            │ ◀───────────────── │  · 配置热加载              │
│                            │   ③ 服务宿主投递    │                            │
└───────────────────────────┘                    └────────────────────────────┘
```

**① 配置文件**是主要通道。配置程序写 `config.json`，服务程序每 2 秒轮询时间戳与大小，
发现变化就重载。这条通道**不需要任何 IPC 机制**，也不需要两个进程同时在线——
服务没运行时改配置，下次启动照样生效。

**② 窗口消息**是次要通道，只用于少数需要立即响应的控制指令：

| 消息 | 值 | 用途 |
|---|---|---|
| `WM_RCK_TRIGGER_DOWN` | `WM_APP + 1` | 钩子 → 窗口过程：触发键按下 |
| `WM_RCK_TRIGGER_UP` | `WM_APP + 2` | 钩子 → 窗口过程：触发键松开 |
| `WM_RCK_SEND_INPUT` | `WM_APP + 3` | 状态机 → 窗口过程：补发被拦截的按键 |
| `WM_RCK_RELOAD` | `WM_APP + 4` | 配置程序 → 服务：立即重新加载配置 |
| `WM_RCK_QUIT` | `WM_APP + 5` | 配置程序 → 服务：退出 |


服务程序的隐藏窗口类名是 `RemapCopilotKey.MessageWindow`，
配置程序用 `FindWindow` 找到它再 `PostMessage`。

**③ 服务宿主**是启动通道（见第 8 节）。配置程序把本程序注册成一个 LocalSystem 的
自动启动服务（SCM），开机后由服务宿主在 Session 0 里启动，它再把钩子进程
**投递进用户会话**（`winsta0\default`），钩子进程拿到的是高完整性令牌。
详见第 8.3 节。

### 两个进程的权限

配置程序与服务程序**同级提权**（都是管理员），清单里都是 `requireAdministrator`。

这是"注册开机自启服务"能成功的前提：SCM 的 `CreateService` 需要管理员权限，
权限不足时只会返回错误 5。早期配置程序是 `asInvoker`，只好
`ShellExecute runas` 拉起服务程序执行 `--install`，失败时只能拿回一个退出码 ——
用户看到的永远是一句"注册失败（退出码 1）"，原因被彻底吞掉。

## 3. 为什么钩子进程不是 Windows 服务

项目里的"服务程序"（`RemapCopilotKeyService.exe`）在**钩子模式**下不是 Windows 服务，
而是运行在用户交互式会话里的提权后台进程。原因是硬性的：

- `WH_KEYBOARD_LL` 是**线程级**钩子，需要安装它的线程有消息循环，并且必须能访问
  **交互式桌面**。
- 真正的 Windows 服务跑在 **Session 0**，与用户会话的窗口站 / 桌面隔离，
  **收不到交互桌面的按键**。

所以能做的是"以管理员权限、在用户会话里、开机自启的常驻进程"。

同一个 exe 还有**服务模式**（`--service`）：这时它是货真价实的 Windows 服务，跑在
Session 0，**不装钩子、也不收按键**，只负责一件事 —— 把钩子进程投递进用户会话。
把"在 Session 0 拿令牌"和"在用户桌面装钩子"拆给两个进程，是这个项目自启方案的
全部要点。见第 8.3 节。

## 4. 键盘钩子与序列状态机

### 4.1 两个独立的状态机

按下和松开是两条独立的序列（拷贝自微软规范里的顺序）：

```
按下： Idle ──LWIN──▶ LeftWindows ──LSHIFT──▶ LeftShift ──F23──▶ 【触发】
松开： Idle ──F23──▶ F23 ──LSHIFT──▶ LeftShift ──LWIN──▶ Idle
```

之所以分开，是因为松开序列**不可能被打断**：F23 一松开，后面两个键会立刻跟上。
而按下序列随时可能被打断（用户其实是在按 `Win+Shift+S`）。

### 4.2 按下序列

| 当前状态 | 收到 | 处理 |
|---|---|---|
| 任意 | `LWIN` 按下 | 拦截（`leftWindowsSuppressed`），`state=LeftWindows`，**启动 100ms 定时器** |
| `LeftWindows` | `LSHIFT` 按下 | 拦截（`leftShiftSuppressed`），`state=LeftShift` |
| `LeftShift` | `F23` 按下 | **序列完成**：`state=Idle`、`releaseState=F23`、取消定时器、把两个标志清掉（意味着**不补发**）、投递"触发按下" |
| `LeftWindows` / `LeftShift` | 其它键按下 | **序列被打断**：先按 `LWIN → LSHIFT` 补发被拦截的键，再把当前键**拦截并重新注入** |

最后一条是保证**事件顺序正确**的关键。如果直接放行，用户按 `Win+E` 会变成"先 E 后 Win"，
开始菜单和资源管理器都会表现异常。所以当前键要先吞掉，排在补发的 LWin 之后。

**打断的三种情况**：

1. 其它键按下
2. **任何键松开**（把这次松开排到补发之后，避免出现"先松开后按下"的顺序错误）
3. 100ms 定时器到期（`WM_TIMER` → `OnChordTimeout()`）

### 4.3 松开序列

| 当前状态 | 收到 | 处理 |
|---|---|---|
| `F23` | `F23` 松开 | 投递"触发松开"，`state=LeftShift`，拦截 |
| `LeftShift` | `LSHIFT` 松开 | `state=LeftWindows`，拦截 |
| `LeftWindows` | `LWIN` 松开 | `state=Idle`，拦截 |

**只有轮到的那一步的松开才被拦截**。所以用户在按住 Copilot 的同时松开左 Shift，
左 Shift 的松开事件会正常传给系统，不会造成 Shift 卡住。

如果松开次序乱了，就放弃拦截（`state=Idle`），宁可多放行也不要卡键。

### 4.4 时序窗口

`kChordTimeoutMs = 100`（`CopilotHook.cpp`）。

Copilot 键是固件级连发，三键间隔通常在毫秒级，100ms 非常宽裕；
而用户手动按 `Win+Shift+...` 时，最后一个键通常远晚于 100ms，
所以定时器到期后会补发并复位，正常按键体验不受影响。

**已知代价**：极慢的蓝牙键盘上，如果三键间隔超过 100ms，Copilot 键不会触发
（此时它会被当成用户手按了 Win 和 Shift，按键本身仍然正常工作）。

### 4.5 兼容被注册表重映射过的 F23

识别 F23 时**同时**看虚拟键码和扫描码：

```cpp
const bool isF23 = (vkCode == VK_F23) || (scanCode == kScanCodeF23);  // 0x6E
```

如果用户用注册表 `Scancode Map` 把 F23 映射成了别的键，`vkCode` 会变，但
`KBDLLHOOKSTRUCT.scanCode` 仍是硬件的 `0x6E`，所以依然能识别。

### 4.6 长按重复

Copilot 键长按时会重复上报 `Win/Shift/F23`。重复的 F23 会重新走一遍状态机，
但此时 `state` 已经是 `Idle`，第一个 LWIN 又会把它带到 `LeftWindows`……
整条序列重放一次，结果是**重复触发**。

对"映射为按键"这类动作，重复触发是无害的（目标键本来就一直按住）；
对"打开应用"这类动作，长按会反复启动程序——这是符合直觉的行为，不做额外抑制。
真要做区分，应参考 NoCopilotKey 的 `targetVKeyNoRepeat` 思路按目标键类型判断。

## 5. 为什么不在钩子回调里调用 SendInput

钩子回调（`LowLevelKeyboardProc`）有**超时限制**，而且 `SendInput` 注入的按键会
**再次进入自己的钩子**，在回调里直接注入容易造成卡顿甚至重入。

所以采用"回调里只投递消息"的结构：

```
钩子回调 ──PostMessage(WM_RCK_*)──▶ 隐藏消息窗口的窗口过程 ──SendInput / ShellExecute──▶ 系统
```

好处：

- 钩子回调永远是常数时间，不会成为输入延迟的来源。
- 注入发生在正常的消息处理里，不存在重入。
- 状态机与动作执行彻底解耦，各自可测。

注入的按键靠 `LLKHF_INJECTED` 标志识别并**直接放行**，避免自激。

## 6. 注入的完整性

`SendInput` 只填 `wVk` 是不够的：很多游戏和 DirectInput 程序**只认扫描码**。
所以注入时同时提供扫描码与扩展位：

```cpp
const UINT scan = VKeyToScanCode(vkey, extended);
input.ki.wScan = scan & 0xFF;
if (scan >= 0xE000 || extended) input.ki.dwFlags |= KEYEVENTF_EXTENDEDKEY;
```

`VKeyToScanCode()` 修补了 `MapVirtualKeyW` 的若干歧义：

| 情况 | 处理 |
|---|---|
| 方向键 / PageUp / PageDown / Home / End / Insert / Delete / NumLock / 右Shift 也存在于小键盘 | 按"是否扩展键"决定是否 OR `0xE000` |
| 小键盘回车 vs 主回车 | 扩展位时 OR `0xE000` |
| PrintScreen vs SysRq | 扩展位时返回 `0xE037` |
| Pause 的扫描码 `MapVirtualKey` 给错 | 硬编码为 `0x45` |

`IsAlwaysExtendedKey()` 列出了必须带扩展位的键（右 Ctrl、右 Alt、方向键、小键盘除号……），
调用方没明确指定时会自动套用，避免把右 Ctrl 注入成小键盘上的别的键。

## 7. 管理员窗口与卡键

低级键盘钩子受 **UIPI** 限制：非提升进程看不到送往提升窗口的输入。

如果服务以管理员身份运行，钩子就能看到所有输入。但还有一个边界情况：
用户在**按着注入的 Ctrl** 的同时把焦点切到管理员窗口，此时系统可能吞掉我们注入的
Ctrl 松开事件，导致 **Ctrl 永久卡住**。

处理方式：

- 用 `SetWinEventHook` 监听 `EVENT_SYSTEM_FOREGROUND`（同时监听
  `EVENT_SYSTEM_MINIMIZEEND` 与 `EVENT_OBJECT_FOCUS`）。
- 前台窗口变化时，用 `OpenProcessToken` + `TokenElevationType == TokenElevationTypeFull`
  判断新前台窗口是否属于提升进程。
- 从"提升窗口"切回"非提升窗口"时，如果还有自己注入且未松开的按键，
  立刻补发松开（`ActionExecutor::ForceReleaseAll()`）。

`WM_ENDSESSION` 与 `WM_DESTROY` 时也会强制释放，避免注销 / 退出时留下按住的按键。

## 8. 提权与开机自启

### 8.1 清单与两种跑法

同一个 `RemapCopilotKeyService.exe` 有两种跑法：

| 跑法 | 谁拉起 | 会话 / 身份 | 干什么 |
|---|---|---|---|
| 钩子模式（默认 / `--run`） | 服务宿主投递，或用户手动双击 | 用户交互会话，管理员（高完整性） | 装 `WH_KEYBOARD_LL` 钩子、跑状态机、执行动作 |
| 服务模式（`--service`） | SCM（开机自动启动 / 界面上的「启动服务」） | Session 0，LocalSystem | 把钩子进程投递进用户会话并守着它；**自己不装钩子** |

两个 exe 的清单都是 `requireAdministrator`（**同级提权**）：

- 服务程序：低级键盘钩子受 UIPI 限制，非提升进程看不到送往提升窗口的输入。
  手动双击会弹一次 UAC（期望行为）；由服务宿主投递时令牌本来就是完整的，
  **不再弹 UAC**。
- 配置程序：调 SCM 注册 / 删除服务需要管理员权限。早期它是 `asInvoker`，
  只好 `ShellExecute runas` 拉起服务程序执行 `--install`，失败时只能拿回一个
  退出码，真正的原因（权限？路径？）全被吞掉。

清单**不参与服务启动**：SCM 用服务账户（LocalSystem）直接建令牌，exe 里写
`requestedExecutionLevel` 对它没有任何影响。所以清单既不能"给服务提权"，
也不会因为写了 `requireAdministrator` 就让服务起不来 —— 这两点恰好是排查
这类问题时最容易先搞错的地方。

### 8.2 为什么钩子进程不能自己当 Windows 服务

- `WH_KEYBOARD_LL` 是**线程级**钩子，需要安装它的线程有消息循环，并且必须能访问
  **交互式桌面**。
- 真正的 Windows 服务跑在 **Session 0**，与用户会话的窗口站 / 桌面隔离，
  **收不到交互桌面的按键**。

所以"装钩子"这件事只能在用户会话里做。反过来，"拿到一个不受 UAC 过滤的完整令牌"
这件事在用户会话里做不到（要么弹 UAC，要么令牌被过滤），只有在 Session 0 里、
以服务身份才做得到。于是拆成两个进程：**服务宿主负责拿令牌，钩子进程负责装钩子**。

### 8.3 开机自启 = LocalSystem 服务 + 会话投递

#### 注册（配置程序侧，`src/Configurator/ServiceInstaller.cs`）

配置程序本身就是管理员，直接用 SCM 的 P/Invoke 注册，不需要任何 COM 互操作程序集：

| 项目 | 值 |
|---|---|
| 服务名 | `RemapCopilotKeyAgent` |
| 显示名 / 描述 | 语言包里的 `service.displayName` / `service.description` |
| 启动类型 | `SERVICE_AUTO_START`（自动） |
| 登录身份 | `LocalSystem`（`lpServiceStartName` 传 `NULL`） |
| 二进制路径 | `"<安装目录>\RemapCopilotKeyService.exe" --service` |
| 失败动作 | 5 秒 / 15 秒 / 60 秒各重启一次，计数器 24 小时清零 |
| 已存在时 | 不报错，改成新配置（覆盖安装 / 换目录都走这条） |

注册完顺手清掉旧版本留下的计划任务（`schtasks /Delete /TN RemapCopilotKey /F`）：
不清的话，登录时计划任务会再拉起一个**低完整性**的钩子进程，和服务投递的那个
抢同一个窗口类名，谁先起来谁赢 —— 排查起来极其迷惑。

#### 投递（服务宿主侧，`src/Service/src/ServiceHost.cpp`）

服务宿主在 Session 0 里以 LocalSystem 身份运行，启动后：

1. `RegisterServiceCtrlHandlerExW` 注册控制处理，进入「正在启动」状态；
2. 打开四个特权：`SeTcbPrivilege`、`SeAssignPrimaryTokenPrivilege`、
   `SeIncreaseQuotaPrivilege`、`SeImpersonatePrivilege`（缺一个都会在下一步被拒）；
3. 每秒一次 `WTSEnumerateSessionsW`，挑出 `State == WTSActive` 且 `SessionId != 0`
   的会话；
4. 对每个还没有子进程的会话：`WTSQueryUserToken` → `DuplicateTokenEx`
   （`TokenPrimary`）→ 若令牌被 UAC 过滤则用 `TokenLinkedToken` 换成完整令牌 →
   `SetTokenInformation(TokenSessionId)` → `CreateProcessAsUserW`
   （桌面 `winsta0\default`、`SW_HIDE`、同一个 exe 带 `--run`）；
5. 子进程塞进一个 `KILL_ON_JOB_CLOSE` 的作业对象：服务被强杀时子进程不会变成孤儿；
6. 每秒收一遍子进程：已退出或会话消失的关掉句柄，会话还在但子进程没了的重新投递。

失败时的日志都写进 `RemapCopilotKey.boot.log`，并且区分两种最常见的原因：
错误 1314 `ERROR_PRIVILEGE_NOT_HELD`（特权没打开，检查服务是不是跑在 LocalSystem 下）
与错误 5 `ERROR_ACCESS_DENIED`（会话还没就绪，通常是登录后紧接着就触发了投递）。

#### 停止、重启与多会话

- 界面上的「停止服务」= `ControlService(SERVICE_CONTROL_STOP)`：服务宿主收到后
  结束所有子进程再报告已停止。
- 「结束并清除服务」= 停 + `DeleteService` + 清旧计划任务，一次做完。
- 快速用户切换 / 多用户同时登录时，每个活跃会话各投递一个钩子进程；注销那个会话
  就收掉对应的那个。
- 钩子进程被任务管理器杀掉时，服务 1 秒内会重新投递 —— 这也顺手解决了
  "用户手滑把关掉的服务" 这类问题。

#### 现状

自启的实际判据只有一个：`boot.log` 里钩子进程那一行必须是
`完整性=高(0x3000)` 且 `会话` 不为 0。服务宿主自己那一行是 Session 0 +
LocalSystem，属于正常现象，不用管它。

### 8.4 历史：计划任务那条路（已废弃，别再走回去）

**症状：计划任务拉起来的钩子进程是低完整性(0x1000)，键盘钩子收不到任何按键。**
计划任务这条路已经整体删掉（连 `TaskScheduler` 的 COM 引用一起），但踩过的坑值得留着。
当时的实测（`RemapCopilotKey.boot.log`，它不受 `logLevel` 影响）：

```
21:40:39 进程启动 pid=11644 模式=run
21:40:39 运行环境: 账户=LAPTOP-DR4R4LO\ASUS 会话=1 窗口站=WinSta0 桌面=Default 完整性=低(0x1000) 提权=是
21:40:46 进程启动 pid=24980 模式=run
21:40:46 运行环境: ... 完整性=低(0x1000) 提权=是          ← 计划任务启动
21:40:54 进程启动 pid=25328 模式=run
21:40:54 运行环境: ... 完整性=高(0x3000) 提权=是          ← 直接启动
```

`提权=是` + `完整性=低(0x1000)` 这个组合是关键：UAC 过滤令牌的 `TokenIsElevated`
是 `FALSE`（那种情况会显示"否"），所以这不是 UAC 过滤，而是计划任务程序发出的
**受限令牌**。进程确实提权了，却被压在低完整性上 —— 钩子装得上、日志照写、不报任何错，
但受 UIPI 限制**一个按键都收不到**。

#### 五种任务形状全部失败

| 任务形状 | 结果 |
|---|---|
| `schtasks /Create /SC ONLOGON /TR ... /RL HIGHEST`（不带 `/RU`） | ❌ 低完整性 |
| 任务定义里写 `<RequiredPrivileges>` | ❌ 注册直接失败 |
| 主体 `GroupId` + 显式 `TASK_LOGON_INTERACTIVE_TOKEN` | ❌ 登录方式被强制改写成 `TASK_LOGON_GROUP` |
| 主体 `UserId` + `TASK_LOGON_INTERACTIVE_TOKEN` + `HighestAvailable` | ❌ **仍是低完整性** |
| 启动时触发 + 主体 SYSTEM + Session 0 宿主 + `CreateProcessAsUser` | ❌ SYSTEM 任务同样是受限令牌 |

- **不带 `/RU` 的 `schtasks /SC ONLOGON`**：ONLOGON 的语义是"**任何用户**登录时运行"，
  主体退化成按组激活。只补 `/RU` 也不行 —— schtasks 文档写明即使对当前用户它也会
  **提示输入密码**，GUI 里会把注册流程挂住。
- **`<RequiredPrivileges>`**：任务定义 **v1.3** 的元素，只允许用在 `LOCAL SERVICE` /
  `NETWORK SERVICE` 这类计算机保留账户的主体上。主体写成登录用户时校验器直接拒绝
  （`(20,57):Privilege:SeImpersonatePrivilege`）。
- **主体 `GroupId`**：`RegisterTaskDefinition` 的 `logonType` 是**函数参数**、不在任务
  定义里，但主体写 `GroupId` 时它会被无视，**强制改写成 `TASK_LOGON_GROUP`** ——
  任务定义 XML 的 schema 也禁止两者共存（`(7,35):LogonType:InteractiveToken`）。
- **主体 `UserId` + `InteractiveToken`**：这是网络上的"标准做法"，回读
  `Principal.LogonType` 确认**确实是** `InteractiveToken`，照样低完整性 ——
  也就是任务定义完全正确，低完整性来自计划任务程序本身。
- **SYSTEM 任务 + Session 0 宿主**：账户是 SYSTEM、`SeTcb`/`SeAssignPrimaryToken`/
  `SeIncreaseQuota` 三个特权也都打开了，`WTSQueryUserToken(会话 1)` 仍然
  报错误码 5（`ERROR_ACCESS_DENIED`）。**受限令牌下调不动 `WTSQueryUserToken`** ——
  这一条直接促成了"换成 SCM 服务"的决定。

**共同点：只要进程是计划任务拉起来的，拿到的就是受限令牌。**
主体的选择（当前用户 / SYSTEM）、登录方式（`InteractiveToken` / `ServiceAccount`）、
运行级别（`HighestAvailable`）都改变不了这一点。

反过来也要说清楚：这条结论**不是**在每台机器上都成立。同一份任务定义在一台
Windows 11 上实测给的是 `高(0x3000)`（用 `Schedule.Service` 建任务、跑
`whoami /groups` 复现），在目标机器上却是低完整性。依赖"计划任务给我什么令牌"的
方案天生不可靠，这才是换掉它的根本原因 —— 不是任务定义写错了。

#### 怎么判断到底成没成

只看 `boot.log` 里钩子进程那一行 `运行环境: ... 完整性=`：必须是 `高(0x3000)`。
**"注册成功"完全不作数** —— 上表每一条都是静默失败。回读 `Principal.LogonType`
只能保证任务定义正确，**保证不了令牌完整性**，这一点已经被实测推翻过一次。

### 8.5 单实例

单实例靠**隐藏窗口类名**判断：服务程序启动时先 `FindWindowW(L"RemapCopilotKeyService.MessageWindow")`，
已经存在就直接退出（并给已有实例发 `WM_RCK_RELOAD`）。不再使用命名互斥体 ——
曾经用过 `Global\RemapCopilotKey.SingleInstance`，但配置程序以不同完整性级别启动时，
打开互斥体会被拒（`ERROR_ACCESS_DENIED`），表现为"第二个实例起来了"。

服务宿主这一侧还有一道："每个会话最多一个子进程"（`SyncChildren` 按会话号记账）。

## 9. 配置热加载

`ConfigWatcher` 轮询文件的**最后写入时间**与**大小**（每秒一次），
两者任一变化就触发重载。第一次轮询只建立基线，不触发。

为什么不用 `ReadDirectoryChangesW`：

- 需要额外的线程与缓冲区管理。
- 对于单个文件的变更，1 秒的轮询成本可以忽略，而且不会漏事件
  （编辑器常见的"写临时文件再改名"也能被时间戳变化捕捉到）。

重载失败时的策略是**降级而不是拒绝启动**：把出错的字段回退成默认值，
记一条警告日志。手改配置写错不该让程序完全不可用。

## 10. 多语言

- 语言包是**嵌入资源** `src/Configurator/Lang/*.json`，运行时枚举资源名加载，
  所以**新增语言不需要改代码**，放进 `Lang\` 重新构建即可。
- 键集一致性由 `ConfigContractTests` 断言（中英文键集必须完全相同），漏翻会直接测试失败。
- 界面刷新通过 `Localization.LanguageChanged` 事件广播，主窗体收到后重新设置所有文本。
- 按键 / 实用功能的**显示名**跟随语言，但**配置文件里存的始终是规范名**
  （`VK_RCONTROL`），所以切换语言不会破坏已有配置。
- 服务程序的对话框也有中英文两套字符串，跟随配置里的 `language`。

## 11. 界面与交互

### 11.1 服务程序没有任何界面

服务程序是**纯后台静默进程**：

- 不创建托盘图标，不创建可见窗口；只有一个 `HWND_MESSAGE` 级别的隐藏消息窗口，
  用来接收定时器、注入请求和控制消息。
- 所有运行状态都写进 `RemapCopilotKey.log`（带级别、时间戳、1 MB 自动轮转）。
- 只有"键盘钩子装不上"这种致命错误才弹一次对话框，其余情况一律静默。

这么做的理由：键盘钩子是常驻的底层设施，托盘图标既是视觉噪音，也会引入
`Shell_NotifyIcon` / 菜单消息循环等一堆与核心功能无关的代码。用户要调配置时有独立的
配置程序，要管理进程时有命令行。

### 11.2 配置程序只写配置

配置程序**不参与按键拦截**。它的职责是三件：

- 唯一的配置输出是 `config.json`；写盘后服务程序靠文件监视
  （或一条 `WM_RCK_RELOAD` 消息）自动重载；写盘由自动保存完成，见 11.3；
- 启停服务（已注册为系统服务时走 SCM 的 Start / Stop，未注册时退回直接拉起
  或 `WM_RCK_QUIT` 消息）；
- 注册 / 删除开机自启服务（见 8.3）。

服务进程本身没有任何界面：它后台静默运行，需要管理时用配置程序或命令行。

### 11.3 界面结构与自动保存

页面顺序是按使用频次排的：

1. 标题 + 语言；
2. **服务管理**卡片（注册服务 / 结束并清除服务 / 启动服务 / 停止服务）—— 日常只有"注册"和
   "卸载"两件事，所以钉在最上面，「注册服务」是主按钮；
3. 映射动作（按键 / 组合键 / 实用功能 / 打开程序 / 打开网页）；
4. 常规设置（启用、热加载、日志级别）；
5. **固定底栏**：打开开源地址 / 状态 + 保存提示 / 恢复默认配置 + 重新读取 + 关闭。

**没有「保存」按钮**。理由：这个界面每一处改动都直接对应一个语义明确的配置项，
"先改再点保存"只会制造一种失败状态（改了但忘了保存、或者关窗时弹窗打断）。
所以改成**防抖自动保存**：

| 机制 | 做法 |
|---|---|
| 触发 | 所有输入控件的事件（勾选、改字、录制完成、下拉选择、切换语言）都走同一个 `QueueAutoSave()` |
| 防抖 | `DispatcherTimer` 600 ms，连续操作只落盘一次 |
| 内容相同不写 | 先把界面收集成配置、序列化成 JSON，与上次保存的 JSON 比字符串，相同就返回 |
| 校验不过不写 | `AppConfig.Validate()` 有问题时**只更新底部提示**（`未保存：原因`），不弹窗、不写盘，避免把能用的配置覆盖成坏配置 |
| 录制中不写 | 任一 `HotkeyBox.IsCapturing` 为真时跳过，避免把"已清空待录入"的中间态写进文件 |
| 写盘后通知 | `ServiceControl.SignalReload()` 发 `WM_RCK_RELOAD`，不用等 2 秒轮询 |
| 关闭窗口 | 停计时器 + 补一次 `AutoSave()`，不再弹"要不要保存" |
| 装配置期间 | `_loading` 标志屏蔽所有自动保存，避免把加载过程写成改动 |

「恢复默认配置」= 确认框 → `new AppConfig()` → `ApplyConfigToUi()` → `AutoSave()`。
`ApplyConfigToUi()` 结束时会重置"上次保存的 JSON"基线，所以恢复默认之后不会被误判成
"有改动"，也不会每 600 ms 重写一次文件。

底部提示位（`SaveHintText`）是这块唯一的反馈通道，文案全部来自语言包：
`status.autoSave` / `status.autoSaveDirty` / `status.autoSaved` /
`status.autoSaveBlocked` / `status.saveFailed`，键集由 `Configurator.Tests` 守着。

### 11.4 输入捕获式快捷键设置

配置界面里选择按键/组合键不是下拉列表，而是**直接按键录制**（`HotkeyBox` 控件）：

- 点一下输入框，按下键盘，捕获到的按键立刻显示出来（如 `右 Ctrl`）。
- 组合键是**三个独立的框**，每个框只录一个键。
- 用 `PreviewKeyDown` 捕获，并在处理完后设 `e.Handled = true`，
  这样 Tab / 方向键等导航键不会被 WPF 拿去切焦点，而是被当成输入录下来。
- 输入法 / 伪键码（`0x15` KANA、`0xE5` PROCESSKEY）会被丢弃，只接受键表里有定义的实体键。
- 修饰键用 `GetAsyncKeyState` 区分左右，所以录出来是 `左 Ctrl` / `右 Ctrl` 而不是"Ctrl（通用）"。
- 捕获结果按顺序转成规范键名（`VK_CONTROL` / `VK_SHIFT` / `VK_ESCAPE`）写入配置。

**已知限制**：Windows 键会被操作系统抢先处理，普通窗口收不到它的 `WM_KEYDOWN`，
因此捕获不到。需要 Win 组合时使用预置的系统功能，或手工编辑配置文件。

### 11.5 布局与高 DPI

界面是 WPF：XAML 描述布局（`MainWindow.xaml` + `Themes/Styles.xaml` 里的
浅色 Win11 卡片样式），文本在代码里统一设置。

- 尺寸全部用**与设备无关的单位**，WPF 自己按 DPI 缩放，所以 125% / 150% 下
  不需要手工调行高，也不会出现像素级模糊。
- 卡片式布局 + `ScrollViewer`：窗口宽度固定、高度由内容决定，
  屏幕装不下时靠滚动访问底部控件（`ClampToWorkArea` 保证标题栏和底部操作栏
  始终可见）。
- 高 DPI 只在 `app.manifest` 里声明 `dpiAware` / `dpiAwareness=PerMonitorV2`。
  （.NET 6+ 的 WinForms 反而必须放在 `ApplicationHighDpiMode` 项目属性里，
  写清单会报 `WFAC010`——本项目已不用 WinForms。）

### 11.6 为什么仍然用代码设置文本

多语言需要在运行时切换**全部**文本。XAML 里写死的文本要么用绑定、
要么用资源字典，两者都会在"再加一种语言"时扩散到很多文件；
（早期 WinForms 版本如此，迁移到 WPF 时保持了这一约定。）

真正需要联动的只有"某个单选按钮是否勾选 → 对应那一组控件是否可用"，
这一层用 `ElementName` 绑定在 XAML 里声明（见 `MainWindow.xaml`），
不再写代码逐个控件设置 `IsEnabled`。

## 12. 模块划分

### C++ 服务程序

| 模块 | 职责 | 依赖 |
|---|---|---|
| `Json` | 自带的 JSON 解析 / 序列化 | 无 |
| `Log` | 日志（文件 + 调试器输出，自动轮转） | 无 |
| `Keys` | 虚拟键名 ↔ 键码 | 无 |
| `Config` | 配置模型、读写、热加载监视、路径与 UTF-8 工具 | `Json`、`Keys`、`Log` |
| `Actions` | 动作执行、按键注入、扫描码修正、实用功能展开 | `Config`、`Keys`、`Log` |
| `AutoStart` | 权限判断与运行环境描述（会话 / 窗口站 / 桌面 / 完整性） | 无 |
| `ServiceHost` | `--service` 模式：SCM 服务宿主，把钩子进程投递进用户会话 | `Log`、`AutoStart` |

依赖是单向的，没有环。`Json` / `Keys` / `Log` 是叶子模块，可以单独测试。

### C# 配置程序

| 模块 | 职责 |
|---|---|
| `AppConfig` | 配置模型 + JSON 读写 + 校验（**唯一**与 C++ 侧对应的部分） |
| `Json` | 自带的极简 JSON 读写（net48 没有 System.Text.Json） |
| `Localization` | 语言包加载与切换 |
| `KeyCatalog` | 键位与实用功能目录、显示名 |
| `HotkeyBox` | 单键捕获控件 |
| `ServiceInstaller` | 开机自启服务（`RemapCopilotKeyAgent`）的注册 / 启动 / 停止 / 删除，走 SCM 的 P/Invoke，顺手清掉旧版本的计划任务。见第 8.3 节 |
| `ServiceControl` | 找服务窗口、发消息、启动 / 停止服务、路径 |
| `SingleInstance` | 单实例（命名互斥体）+ 激活已有窗口 |
| `MainWindow` | 界面 |

> 服务注册放在**配置程序**而不是服务程序里，是刻意的：
> 它属于"配置"而不是"运行时"；而且配置程序本身已经提权，可以直接调 SCM，
> 服务程序侧就不必再留一套"被 runas 拉起来执行安装参数"的入口。
>
> 配置程序还提供两个给安装包用的开关：`--register-service` / `--unregister-service`
> —— Inno Setup 在装完 / 卸前各调一次，用户装完就是"自启已注册、服务已在跑"。

## 13. 测试策略

三个测试套件，共约 358 项断言：

| 套件 | 语言 | 断言数 | 重点 |
|---|---|---|---|
| `json_test` | C++ | 68 | 自带 JSON 解析器的语法、转义、UTF-8、代理对、错误定位、深度限制 |
| `config_test` | C++ | 164 | 键名往返、配置解析、五类动作、异常回退、UTF-8 路径 |
| `ConfigContractTests` | C# | 126 | JSON 字段名、序列化幂等、校验逻辑、键表唯一性、语言包键集一致、**C# 侧自带的 JSON 层** |

**跨语言闭环**是这个项目最重要的测试：C# 测试会写出一份样例配置，
构建脚本再把它的路径传给 C++ 的 `config_test`，由后者解析并逐项核对。
字段名一旦改动就会立刻失败——而字段名不一致是这类"双端共享配置"项目最容易出的问题。

C# 侧自带的极简 JSON 层（`src/Configurator/Json.cs`，替代 net48 缺失的
`System.Text.Json`）同样由 `TestJsonLayer` 覆盖：转义、代理对、缩进格式、
手改配置常见的注释与尾逗号、错误定位。它替代了一个成熟库，
所以这部分断言是必要的，不是锦上添花。

## 14. 未采用的方案：键盘过滤驱动

排查"能否复用已有签名驱动"时得到的结论：

- 唯一通用的现成方案是 [Interception](https://github.com/oblitum/Interception)
  （`kbdclass` 上层过滤驱动）。它确实是驱动级的：能覆盖 UAC 桌面、登录界面、游戏，
  不受 UIPI 限制。
- 但最后一个 release 是 **v1.0.1（2017 年）**，用 **WDK 7.1** 构建，只声明测试到
  Windows 10；驱动签名来自作者个人的 GlobalSign 代码签名证书（**2012 年过期的交叉签名**），
  不是微软 WHQL / attestation 签名；并且已知有"客户端崩溃导致键鼠失效到重启"和
  "Secure Boot 机器上安装失败"的问题。
- 自写驱动需要 EV 代码签名证书 + 微软 Partner Center attestation 签名，
  成本与维护负担都不低。

结论：以 **用户态钩子** 为主线，把驱动方案留作后续可选路径。
这也意味着**安全桌面覆盖不到**，属于已知限制。

## 15. 附录：配置文件格式

配置文件名为 `config.json`，放在**程序目录**（服务程序与配置程序所在的那个目录），
编码为 **UTF-8 无 BOM**。

服务程序每 2 秒检查一次文件的时间戳与大小，发现变化就立刻重新加载，
所以改完**直接保存即可生效**，不需要重启（前提是 `mapping.reloadOnChange` 为 `true`）。

> 手改配置文件出错不会让服务起不来：非法的单项会回退成默认值，
> 同时在日志里记一条警告。

### 完整结构

```json
{
  "version": 1,
  "language": "zh-CN",
  "logLevel": "info",
  "enabled": true,

  "mapping": {
    "trigger": "copilotKey",
    "reloadOnChange": true,
    "action": {
      "type": "sendKey",
      "vkey": "VK_RCONTROL"
    }
  }
}
```

### 字段说明

#### 顶层

| 字段 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `version` | 整数 | `1` | 配置格式版本。目前只有 1。 |
| `language` | 字符串 | `"zh-CN"` | 界面语言，对应 `src/Configurator/Lang/` 下的语言包代码。影响配置程序界面与服务程序对话框。 |
| `logLevel` | 字符串 | `"info"` | 日志级别：`off` / `error` / `warn` / `info` / `debug`。排查问题时改成 `debug`。 |
| `enabled` | 布尔 | `true` | 总开关。为 `false` 时键盘钩子仍然安装，但不拦截任何按键。 |


#### `mapping`

| 字段 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `trigger` | 字符串 | `"copilotKey"` | 触发方式。目前只支持 `copilotKey`（即 `左Win + 左Shift + F23` 序列）。其它值会被回退成 `copilotKey` 并记警告。 |
| `reloadOnChange` | 布尔 | `true` | 配置文件变化时是否自动重新加载。 |
| `action` | 对象 | 见下文 | 触发时执行的动作。 |

---

### `mapping.action` 的五种写法

#### 1. 映射为按键（`sendKey`）

按住 Copilot 键时目标按键保持按下，松开时一起松开。这是默认动作。

```json
{ "type": "sendKey", "vkey": "VK_RCONTROL" }
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `vkey` | 字符串 | 是 | 目标按键名。写错会回退成 `VK_RCONTROL`。 |

> **为什么默认是右 Ctrl**：微软要求没有多余键位的键盘用 Copilot 键替换右 Ctrl，
> 这个动作就是把右 Ctrl 还回去。选 `VK_CONTROL`（通用 Ctrl）也可以，
> 系统会自行解析成左右 Ctrl。

#### 2. 映射为组合键（`sendChord`）

按一下 Copilot 键，就发送一次完整组合键（依次按下，再逆序松开）。

```json
{ "type": "sendChord", "keys": ["VK_CONTROL", "VK_SHIFT", "VK_ESCAPE"] }
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `keys` | 字符串数组 | 是 | 按下顺序排列的按键名。空数组会回退成 `Ctrl+Shift+Esc`。数组里无法识别的项会被忽略并记警告。 |

> 配置程序里这一项是**输入捕获**式的：点一下输入框，然后直接按键盘即可录制，
> **最多三个键**（例如 `Ctrl + Shift + Esc`）。
> 注意 Windows 键会被操作系统抢先处理，普通窗口捕获不到；需要 Win 组合请直接用
> 下面的 `systemAction` 预置项，或手工在配置文件里写 `VK_LWIN`。

#### 3. 打开应用程序（`openApp`）

```json
{ "type": "openApp", "path": "C:\\Windows\\System32\\notepad.exe", "args": "" }
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `path` | 字符串 | 是 | 可执行文件路径，也可以是任何能被 `ShellExecute` 打开的东西（文档、文件夹）。JSON 里反斜杠要写成 `\\`。 |
| `args` | 字符串 | 否 | 命令行参数。 |
| `runAsAdmin` | 布尔 | `false` | 被打开的程序是否以管理员权限运行（ShellExecute 的 runas 动词）。 |
| `toggleWindow` | 布尔 | `false` | 为 `true` 时，如果该程序**已经在运行**，再次触发只会最小化/还原它的窗口，而不是再启动一个实例。 |

#### 4. 打开网页（`openUrl`）

```json
{ "type": "openUrl", "url": "https://github.com/" }
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `url` | 字符串 | 是 | 交给系统默认浏览器打开。 |

#### 5. Windows 实用功能（`systemAction`）

```json
{ "type": "systemAction", "action": "taskManager" }
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `action` | 字符串 | 是 | 见下表。无法识别会回退成 `explorer`。 |

> **再次按下会关闭**：对于会启动程序的实用功能（资源管理器 / 任务管理器 / cmd /
> PowerShell / 计算器 / 记事本 / 控制面板），如果该程序已经在运行，再次触发会
> **关闭它**（发送 `WM_CLOSE`）；没在运行才启动。发送快捷键的那些
> （截图 / 任务视图 / 剪贴板历史 / 表情面板 / 锁定屏幕）不受影响。

| `action` | 行为 | 中文界面显示 |
|---|---|---|
| `explorer` | 启动 `explorer.exe` | 文件资源管理器 |
| `taskManager` | 启动 `taskmgr.exe` | 任务管理器 |
| `cmd` | 启动 `cmd.exe` | 命令提示符 |
| `powershell` | 启动 `powershell.exe` | PowerShell |
| `screenshot` | 发送 `Win+Shift+S` | 截图 |
| `snippingTool` | 打开 `ms-screenclip:` | 截图工具 |
| `settings` | 打开 `ms-settings:` | 设置 |
| `controlPanel` | 启动 `control.exe` | 控制面板 |
| `calculator` | 启动 `calc.exe` | 计算器 |
| `notepad` | 启动 `notepad.exe` | 记事本 |
| `taskView` | 发送 `Win+Tab` | 任务视图 |
| `clipboardHistory` | 发送 `Win+V` | 剪贴板历史 |
| `emojiPanel` | 发送 `Win+.` | 表情符号面板 |
| `lockScreen` | 发送 `Win+L` | 锁定屏幕 |

## 16. 附录：命令行参数

### 命令行参数（服务程序）

| 参数 | 说明 |
|---|---|
| （无） / `--run` | 以钩子模式启动服务（**后台静默运行，无托盘、无界面**） |
| `--service` | 以 Windows 服务宿主模式运行（只给 SCM 用，见下文） |
| `--stop` | 停止正在运行的实例。已停止返回 2 |
| `--config <路径>` | 使用指定的配置文件（默认：程序目录\config.json） |
| `--loglevel <级别>` | 临时覆盖日志级别：off / error / warn / info / debug |
| `--quiet` | 不弹出任何对话框 |
| `--help` | 显示用法 |

> 早期版本还有 `--install` / `--uninstall` / `--status`。
> 开机自启的注册与删除现在由**配置程序**负责
> （见 `src/Configurator/ServiceInstaller.cs`，直接调 SCM 的 CreateService / DeleteService），
> 服务程序侧已移除这三个参数。
>
> **`--service` 是给服务控制管理器用的**：开机自启注册的是 LocalSystem 的自动启动服务
> `RemapCopilotKeyAgent`，SCM 拉起它时带 `--service`；它常驻 Session 0，只负责
> 把钩子进程投递进你的交互会话，自己不装键盘钩子。手动执行 `--service` 会因为不是由 SCM
> 启动而直接退出。见本文第 8.3 节。

### 命令行参数（配置程序）

| 参数 | 说明 |
|---|---|
| （无） | 打开图形界面 |
| `--dump-default-config <路径>` | 写出一份默认配置后退出（不开窗口），用于校验 JSON 契约 |
| `--register-service` | 静默注册开机自启服务（LocalSystem、自动启动、失败自动重启）并启动它，随后退出。安装包用 |
| `--unregister-service` | 静默停止并删除开机自启服务（同时清掉旧版遗留的计划任务），随后退出。卸载包用 |
| `--diagnose` | 把启动过程中的每一步写进 `%TEMP%\RemapCopilotKey.Configurator.log` |
