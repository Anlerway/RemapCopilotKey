记录本项目的构建约定、踩过的坑，以及常见扩展任务的步骤。

## 一、构建约定（务必遵守）

### 1. `.cmd` / `.bat` 必须是纯 ASCII + CRLF

**症状**：脚本运行时出现大量莫名其妙的错误，例如
`'\Microsoft was unexpected at this time'`、`'目录' is not recognized as an internal command`，
甚至 `goto` 标签错乱、行被拼接成莫名其妙的片段。

**原因**：`cmd.exe` 用 **OEM 代码页**（简中系统上是 GBK/936）逐行解析批处理文件。

- 中文注释的 UTF-8 字节被当成 GBK 解码后，**一个 UTF-8 中文字符（3 字节）会与后面的
  ASCII 字符配成 GBK 双字节字符**，从而把 `{`、`)`、`"` 这类结构字符吃掉。
- 只有 LF 行尾时，`goto` / `for` 的解析也会出错。

**对策**：

- 批处理文件**只写 ASCII**（注释也用英文），中文放到 Markdown 里。
- `.gitattributes` 已强制 `*.cmd`/`*.bat` 为 `eol=crlf`。
- 复杂逻辑**不要写在批处理里**——本项目的 `build.cmd` 只是三行包装器，
  真正的逻辑在 `build.ps1`。

### 2. `.ps1` 必须带 UTF-8 BOM

**症状**：`build.ps1` 报 `Missing closing '}' in statement block`，
但用编辑器看语法完全正常。

**原因**：Windows PowerShell 5.1 在**没有 BOM** 时按 ANSI（GBK）解码 `.ps1`。
中文注释的字节又一次吃掉了结构字符——和上面的批处理是同一类问题。
用正确的 UTF-8 解码时 `Parser::ParseInput` 报 0 个错误，用 GBK 解码报 3 个错误，
这就是定位方法：

```powershell
$text = [IO.File]::ReadAllText($path, [Text.Encoding]::UTF8)
$tokens = $null; $errors = $null
[System.Management.Automation.Language.Parser]::ParseInput($text, [ref]$tokens, [ref]$errors)
$errors   # 0 表示编码正确，问题的根因是文件编码而不是语法
```

**对策**：`.ps1` 一律写 UTF-8 **带 BOM**。若用其它工具编辑后 BOM 丢了，补回来：

```powershell
$p = 'build.ps1'
$text = [IO.File]::ReadAllText($p, [Text.Encoding]::UTF8)
[IO.File]::WriteAllText($p, $text, (New-Object Text.UTF8Encoding($true)))
```

> 注意：`write` 之类的工具通常**不带 BOM**，修改 `.ps1` 之后记得检查前 3 字节是不是
> `EF BB BF`。

### 3. C++ 源码：UTF-8 无 BOM + `/utf-8`

C++ 源码里有中文注释，编译时必须加 `/utf-8`，否则 MSVC 会按系统代码页解释，出现
`C4819` 或莫名其妙的字符串截断。`build.ps1` 已经加了。

### 4. 链接器必须加 `/MANIFESTUAC:NO`

**症状**：

```
manifest authoring error c1010001: Values of attribute "level" not equal in different manifest snippets.
LINK : fatal error LNK1327: 运行 mt.exe 期间出错
```

**原因**：`/MANIFESTINPUT:` 传入的自定义 `app.manifest` 里写了
`requireAdministrator`，而 MSVC 默认还会生成一个 `asInvoker` 的 UAC 片段，
`mt.exe` 合并时发现 `level` 冲突。

**对策**：链接选项里同时加 `/MANIFESTUAC:NO` 抑制默认片段：

```
/link /MANIFEST:EMBED /MANIFESTUAC:NO /MANIFESTINPUT:"...\app.manifest"
```

### 5. net48 + WPF 的几个坑（从 .NET 8 / WinForms 迁过来时踩到的）

配置程序现在是 **.NET Framework 4.8 + WPF**。SDK 风格工程指向 net48 时，
有几件事和 net8.0-windows 不一样：

| 现象 | 原因 | 对策 |
|---|---|---|
| `CS0518: 未定义或导入 System.Runtime.CompilerServices.IsExternalInit` | C# 9 的 `init` 访问器 / `record` 需要这个类型，它只在 .NET 5+ 的 BCL 里 | 项目里补一个 `Compat.cs`（空的标记类型），不需要引 NuGet 包 |
| `CS0246: 未能找到类型或命名空间名 System.IO` | net48 + WPF 的隐式 using 比 net8.0-windows + WinForms 少 `System.IO`（见 `obj` 下的 `*.GlobalUsings.g.cs`） | csproj 里加 `<Using Include="System.IO" />` |
| `CS1501: Contains 方法没有采用 2 个参数的重载` | `string.Contains(string, StringComparison)` 是 .NET Core 2.1+ 才有的 | 用 `IndexOf(..., StringComparison) >= 0` 代替 |
| 没有 `Environment.TickCount64`、`AppContext.BaseDirectory` | net48 没有这些 API | 用 `Stopwatch.GetTimestamp()`、`AppDomain.CurrentDomain.BaseDirectory` |
| `dotnet publish` 那一套自带运行时/框架依赖的双包 | net48 是系统自带组件，不需要发布运行时 | 改成 MSBuild 直接出产物 + 一份绿色包（见 `tools/package.ps1`） |

`.ps1` 必须带 UTF-8 BOM 这条（见第 2 条）**与 net48 无关**，但只要构建脚本还在用
Windows PowerShell 5.1 就依然成立 —— 每次改写 `build.ps1` / `tools/package.ps1`
之后都要确认 BOM 还在，否则中文注释会被按 GBK 解码而吃结构字符。

WinForms 的 DPI 设置（`ApplicationHighDpiMode`）已经不再相关：WPF 是分辨率无关的，
高 DPI 只在 `app.manifest` 里声明 `dpiAware` / `dpiAwareness=PerMonitorV2`。
（.NET 6+ 的 WinForms 反而必须放在项目属性里，写清单会报 `WFAC010`。）

### 5b. XML 注释里的连续两个减号会让 exe 起不来

**症状**：打出来的 exe 双击直接弹

```
应用程序无法启动，应用程序的并行配置不正确
```

进程在 `Main` 之前就被终止 —— 没有堆栈、没有日志、调试器也断不下来。

**原因**：`app.manifest` 也是 XML，而 XML 规范**禁止注释里出现连续两个减号**。
清单注释里只要写了 `--install` 这样的命令行参数，整个清单就成了非法 XML，
Windows 加载激活上下文时直接失败。

**对策**：

- 注释里不要出现连续减号，`--install` 写成"那个安装参数"或 `- -install`。
- 构建脚本已经加了预检：`tools/check-xml.ps1` 会扫描 `*.manifest` / `*.xaml` /
  `*.csproj` / `*.config` 等文件里的非法注释，发现问题直接让构建失败。
  **这一步必须自己做** —— MSBuild 和 XAML 编译器都不检查 manifest。
- 手动确认一份清单是否合法：

  ```powershell
  $doc = New-Object System.Xml.XmlDocument
  $doc.Load('src\Configurator\app.manifest')     # 抛异常就是非法
  ```

- 另一种定位手段：`sxstrace.exe`（错误提示里就推荐了它）。

> 这个坑的教训是：**报错信息指向的方向（"并行配置"听起来像 DLL 依赖问题）
> 和真实原因（注释写错了）可以完全无关**。凡是"改完清单就起不来"，
> 先用 XML 解析器把清单本身过一遍。

### 5c. 用 XML 文档注释里的 `<` 要小心

XAML 里出现 `<` 必须转义成 `&lt;`，而 C# 的 XML 文档注释里写 `<Delay>` 这类
标签会被当成 XML 结构，导致 `CS1570`。注释里提到 XML 元素时用文字描述，
或写成 `` `<Delay>` ``（放在代码片段里）。

### 5d. 提权要求必须检查**编译产物**，不能只看源码

**症状**：注册开机自启报"权限不足"，但 `src/Configurator/app.manifest` 里明明写着
`requireAdministrator`。

**原因**：某次构建出来的 exe 里嵌的却是 `asInvoker`。源码正确 ≠ 产物正确 ——
清单是在编译时用 `/win32manifest` 嵌进 PE 的，中间任何一步出问题都不会报错。

**对策**：构建后检查 exe 字节流里的清单文本（`tools/check-manifest.ps1`，已接到
`build.ps1` 的 `Build-Config` 里）：

```powershell
# 直接从 exe 的字节流里找清单，比任何间接手段都可靠
$t = [System.Text.Encoding]::UTF8.GetString([IO.File]::ReadAllBytes($exe))
$t.Contains('requireAdministrator')      # 必须是 True
```

> 教训和 5b 一样：**清单是"看起来没问题但能让程序彻底不可用"的地方**，
> 而且诊断信息（"并行配置不正确"、"权限不足"）都不会指向清单。

### 5e. 单实例互斥体会让"双击没反应"

**症状**：双击配置程序，进程立刻以退出码 0 结束，什么都不显示。

**原因**：单实例逻辑发现互斥体已存在，就把已有窗口拉到前台然后退出。
如果上一个实例是**异常结束**（或被调试器杀掉）而互斥体仍被某个进程持有，
新实例就会静默退出 —— GUI 程序没有标准输出，看起来就是"双击没反应"。

**对策**：

- 加 `--diagnose` 启动开关（`src/Configurator/Diagnostics.cs`），把启动每一步写进
  `%TEMP%\RemapCopilotKey.Configurator.log`。GUI 程序没有 stdout，
  这类"静默退出"问题只能靠日志。**`--diagnose` 会跳过单实例检查**，
  否则诊断本身就被单实例挡住了。
- 找不到已有窗口时弹一个提示框，而不是静默退出。

### 6. Windows 头文件不定义 `VK_A`..`VK_Z`

字母键的虚拟键码就是它的大写 ASCII 值，直接写 `L'A'` 即可。
（`VK_0`..`VK_9` 同理。）本项目的 `Keys.cpp` 里有注释标注。

### 7. 沙箱 / 受限环境下的两个现象

- PowerShell 里 `%ProgramFiles(x86)%` 这个环境变量**不保证存在**，
  批处理脚本直接展开它会让 `)` 变成语法符号、整段脚本崩掉。
  用 `$env:SystemDrive` + 字面量路径，或干脆用 PowerShell 的 `Test-Path` 探测。
- 某些环境里 TLS 握手会失败（`SEC_E_NO_CREDENTIALS`），
  下载依赖会失败。本项目**没有任何需要下载的依赖**，这也是自带 JSON 解析器的原因之一。

### 改动"注册服务"（开机自启计划任务）

> ⚠️ **先看结论：这条路径目前不可用。** 计划任务拉起来的服务实例是**低完整性(0x1000)**，
> 键盘钩子收不到任何按键；只有直接启动才是高完整性(0x3000)。完整实测记录见
> `docs/设计说明.md` 第 8.2 节与 `README.md` 的"开机自启：目前不可用"。

实现在 `src/Configurator/AutoStart.cs`，**不在服务程序里**，用计划任务的 **COM 接口**
（`RegisterTaskDefinition`），不是 `schtasks`。

踩过的坑，以及为什么它们仍然不解决问题：

1. **主体退化成按组激活**（主体写 `GroupId`，或用
   `schtasks /Create /SC ONLOGON /TR ...` 那条命令行 —— 不带 `/RU` 时 ONLOGON 的语义是
   "任何用户登录时运行"）。计划任务程序会把登录方式锁成 `TASK_LOGON_GROUP`，
   连 `RegisterTaskDefinition` 里显式传的 `InteractiveToken` 都被无视。
   后果是**低完整性(0x1000)**：钩子装得上、日志照写，但受 UIPI 限制**一个按键都收不到**，
   而"注册成功"完全看不出来。
   只加 `/RU` 也不行：schtasks 文档写明即使对当前用户它也会**提示输入密码**。
2. **`<RequiredPrivileges>`** 是任务定义 v1.3 的元素，任务计划程序只允许把它用在
   `LOCAL SERVICE` / `NETWORK SERVICE` 这些计算机保留账户的主体上。
   主体写成登录用户时校验器直接拒绝（`(20,57):Privilege:SeImpersonatePrivilege`），
   `schtasks /Create /XML` 必然失败、注册永远成功不了。
3. **主体改成 `UserId` + `InteractiveToken` 也没用** —— 任务定义确实正确了
   （`AutoStart.Install` 回读过 `Principal.LogonType`），但启动出来的仍然是
   **低完整性(0x1000)**。
4. **"启动时 + SYSTEM 任务 + Session 0 宿主"同样不行**：SYSTEM 任务拿到的也是受限令牌，
   `WTSQueryUserToken` 直接返回 `ERROR_ACCESS_DENIED`（5）。

**共同点：只要进程是计划任务拉起来的，拿到的就是受限令牌。**

> 判断自启是否真的生效，**只看"注册成功"完全不够**。看 `RemapCopilotKey.boot.log` 里
> 那一行（它不受 `logLevel` 影响）：必须是 `完整性=高(0x3000)`。
> `低(0x1000)` 就说明钩子一定收不到按键。

手上有任务 XML、想确认它合不合法时，**不需要管理员权限也不需要真的注册** ——
用计划任务自己的校验器过一遍即可（`ITaskDefinition::XmlText` 的 setter 走原生校验）：

```powershell
$svc  = New-Object -ComObject Schedule.Service; $svc.Connect()
$task = $svc.NewTask(0)
try   { $task.XmlText = [IO.File]::ReadAllText('task.xml'); 'VALID' }
catch { 'INVALID -> ' + $_.Exception.Message }   # 形如 (20,57):Privilege:SeImpersonatePrivilege
```

要看**已经注册的**任务定义，用配置程序的诊断开关（UTF-8，同时打印关键字段）：

```bat
RemapCopilotKey.exe --export-task task.xml
```

> 注意：配置程序带 `requireAdministrator` 清单，直接跑会先弹一次 UAC。

### 开机自启不生效时的排查顺序

**先记住结论**：注册成功 ≠ 能工作。注册出来的是普通登录任务，**拉起的实例一定是
低完整性(0x1000)**，钩子收不到按键 —— 这是当前已知问题，不是配置错误。

1. **看 `RemapCopilotKey.boot.log`**（程序目录，不受 `logLevel` 影响）。
   找 `运行环境: ... 完整性=` 那一行：
   - `高(0x3000)` → 这个实例是直接启动的，正常；
   - `低(0x1000)` + `提权=是` → 计划任务拉起来的，钩子必然收不到按键。
2. **确认没有残留的自启任务**。留着任务会让「启动服务」改走计划任务：
   点「结束并清除服务」删掉它，再手动「启动服务」。
3. **注册本身失败**（弹框报错）时：
   - 权限不足：确认以管理员身份运行。构建后用 `tools/check-manifest.ps1`
     确认 exe 里真的嵌了 `requireAdministrator`（源码正确 ≠ 产物正确，这条踩过）。
   - 找不到路径：确认 `RemapCopilotKeyService.exe` 与配置程序在同一个目录下。
   - 登录方式被改写成 `TASK_LOGON_GROUP`：`--export-task` 看系统里实际存的是什么，
     再到"任务计划程序"里删掉 `RemapCopilotKey` 后重试。
4. 需要看详细的按键流时把 `logLevel` 调成 `debug`，日志是同目录的
   `RemapCopilotKeyService.log`。

## 四、代码风格

- C++：`/W4 /permissive- /std:c++20`，**零警告**是硬要求。
  - 类型 / 函数 `PascalCase`，局部变量 `camelCase`，成员 `m_` 前缀。
  - 头文件用 `#pragma once`。
  - 注释用中文，解释**为什么**而不是**做什么**。
- C#：`TreatWarningsAsErrors=true`，可空引用类型开启。
  - 私有静态字段 `s_` 前缀。
  - 同样解释"为什么"。
- 提交前跑一次 `build.cmd`（构建 + 全部测试）。
